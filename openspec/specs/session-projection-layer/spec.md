# session-projection-layer Delta

## ADDED Requirements

### Requirement: Projection trait

The change SHALL define a projection abstraction with three pure functions: `init` (empty-log state), `apply` (state + one event → next state), `view` (state → wire format).

#### Scenario: Deterministic fold

- GIVEN the same event sequence
- WHEN the projection is applied twice from `init`
- THEN both runs SHALL produce identical state
- AND the fold SHALL be a pure function of the events (no external state, no time dependence)

#### Scenario: Incremental apply

- WHEN a new event is appended
- THEN the projection SHALL apply only the new event to the existing state (O(new events), not O(full log))
- AND the result SHALL equal a full re-fold from `init`

#### Scenario: Squash semantics

- GIVEN a `history/squash` event with `base_seq` and a summary message
- WHEN the projection folds it
- THEN message events at or below `base_seq` SHALL be dropped from the projection state
- AND the summary message SHALL be injected (compaction does not resurrect squashed history)

### Requirement: Snapshot as projection cache

`SessionSnapshot` SHALL be derivable from `turn_events` via projections; the blob snapshot SHALL be a cache, not the source of truth.

#### Scenario: Rebuild equivalence (bounded field set)

- GIVEN a session with persisted events and a reference snapshot
- WHEN the snapshot is rebuilt from events via projections
- THEN the rebuilt snapshot SHALL match the reference snapshot on the agreed field set (history, turn_trace_history, plan state, metrics-derived fields)
- AND fields outside the agreed set (history_nodes, history_branches, history_cursor, long_term_memory_entries, memory_write_evidence, provider_native_transcript, attachment catalog) SHALL NOT participate in the comparison (covered by regression tests)

#### Scenario: Cache invalidation

- WHEN events are appended
- THEN the cached snapshot SHALL be updated incrementally (or invalidated and rebuilt on next read)
- AND readers SHALL never observe a snapshot older than the last committed event

### Requirement: append_turn refactor

`append_turn` SHALL append events and fold projections instead of pushing messages into a mutable snapshot and re-serializing the whole blob.

#### Scenario: Projection-generated snapshot

- GIVEN a turn with N new events
- WHEN `append_turn` runs
- THEN the snapshot SHALL be generated by `view(projection state)` (no hand-maintained message push)
- AND the full-blob re-serialization SHALL remain in the hot path until phase 4 (write-amplification elimination is deferred, not claimed here)

#### Scenario: Behavior preservation

- WHEN `append_turn` runs under the refactor
- THEN the resulting snapshot SHALL be identical to the reference implementation on the agreed field set (history content, metadata, truncation semantics)

### Requirement: Trace as projection

`TurnTraceRecord` SHALL be derived from events via `TraceProjection`; the trace table SHALL be a persisted projection cache with a seq watermark.

#### Scenario: Trace rebuild

- GIVEN persisted events for a turn
- WHEN the trace is rebuilt from events
- THEN the rebuilt `TurnTraceRecord` SHALL match the stored record on the agreed field set (tool activities, timeline entries, token metrics)
- AND fields with clock/sequence semantics (`updated_at`, `event_id`, `sequence`, `emitted_at_ms`) SHALL be exempted (explicit exemption list)

#### Scenario: Watermark idempotency

- WHEN the trace cache is replayed
- THEN events at or below the watermark SHALL NOT regress the cache (higher seq wins)
- AND a cleared cache SHALL rebuild to the same value from events

### Requirement: Metrics projection

Token usage, cache accounting, and latency metrics SHALL be derived from events via `MetricsProjection`; model monitor views SHALL read the projection cache, not scan trace data.

#### Scenario: Totals rebuild

- GIVEN persisted `ProviderUsage` events
- WHEN totals are rebuilt from events
- THEN the four buckets (uncached input / cache read / cache write / output) SHALL match the accumulated values
- AND the per-turn aggregation SHALL match the model monitor drilldown

#### Scenario: Add-replacing semantics

- WHEN a step reports updated usage (replacement, not accumulation)
- THEN the totals SHALL replace the previous usage for that step (addReplacing, no double count)
- AND `assistant/message` usage SHALL NOT contribute to totals (metadata display only, no double counting)

#### Scenario: Monitor views from cache

- WHEN `load_model_monitor_summary` / `load_model_monitor_session_drilldown` run
- THEN they SHALL read from the `MetricsProjection` persisted cache (seq-watermarked)
- AND a cleared cache SHALL rebuild to identical values from events

### Requirement: Golden-fixture comparison

The projection SHALL be verified against a reference implementation using golden fixtures.

#### Scenario: Fixture corpus

- GIVEN the synthetic corpus matrix (empty session, single-event turn, truncation boundary, tool chains, multi-hop provider usage, checkout/fork events, `chunk_missing`, `history/squash`, 10k+ events, 100KB+ payload)
- WHEN each fixture is folded by the projection and by the reference implementation
- THEN the results SHALL match on the agreed field set

#### Scenario: Verify mode

- GIVEN `PONY_AGENT_PROJECTION_VERIFY=record` (CI/test)
- WHEN a projection difference is detected
- THEN the run SHALL fail (difference is an error)
- GIVEN `PONY_AGENT_PROJECTION_VERIFY=sample` (production sampling)
- WHEN a projection difference is detected
- THEN the difference SHALL be logged, not panic (production hot path never crashes on projection drift)
