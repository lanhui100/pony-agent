# trace-event-projection Specification

## Purpose

规范 trace 事件化（ADR 0008 阶段 4，任务卡 `PA-094`）后 trace 投影的运行时契约：trace 表降级为 `TraceProjection` 的持久化缓存（事件权威、清表可重建、每行携带 seq 水位），`trace_timeline` 按事件映射表折叠、`provider_call_records` 由 `MetricsProjection` 从 `ProviderUsage` 事件生成，前端 trace 视图与消息视图从同一份事件派生，大字段（`build_context_observation`）以引用外置存储并按需加载。本文件原为 delta 格式，2026-09-30 依 PA-102 按 canonical 格式规范化，语义未变。

## Requirements

### Requirement: Trace as projection cache

The trace table SHALL be a persisted cache of `TraceProjection`, rebuildable from events (events are authoritative; the stored record is a cache).

#### Scenario: Cache rebuild

- GIVEN persisted events for a session
- WHEN the trace table is cleared
- THEN the traces SHALL rebuild to values consistent with the event fold via `TraceProjection`

#### Scenario: Watermark semantics

- WHEN the trace cache is updated
- THEN each row SHALL carry the seq watermark of the last folded event
- AND replay at or below the watermark SHALL NOT regress the cache

### Requirement: Timeline from events

`trace_timeline` entries SHALL be folded from events per the mapping table: `step/start` → `call_model`, `tool/call` → `call_tool`, `tool/result` → `return_result`.

#### Scenario: Timeline derivation

- GIVEN a turn with steps, tool calls, and results
- WHEN the timeline is built from events
- THEN each `TraceTimelineEntry` SHALL correspond to one event per the mapping table (table-driven test)
- AND the entry sequence SHALL match the event order

#### Scenario: Timeline equivalence

- WHEN the timeline is rebuilt from events
- THEN it SHALL match the previously stored timeline on the agreed field set
- AND clock/sequence fields (`updated_at`, `event_id`, `sequence`, `emitted_at_ms`) SHALL be exempted (explicit exemption list)

#### Scenario: Tool activity rebuild

- GIVEN `ToolCall`/`ToolResult` events with extended fields (started_at_ms, duration_ms, status, artifacts, capability_invocation)
- WHEN `TurnToolActivity` is rebuilt
- THEN `duration_seconds`, `status`, `artifacts`, `capability_invocation` SHALL be reconstructed from the event fields

### Requirement: Frontend single-source views

The frontend trace view and message view SHALL derive from the same event source.

#### Scenario: Same-source rendering

- WHEN the frontend renders a turn's messages and its trace
- THEN both SHALL be derived from the same persisted event stream (no independent trace data path)
- AND the wire format consumed by the frontend SHALL remain backward compatible (or migrate with explicit versioning)
- AND the frontend rendering projection (`trace-projection.ts`) SHALL remain (same-source means same event-derived wire data, not removal of the render projection)

### Requirement: Large-field externalization

`build_context_observation` (and similar large fields) SHALL be stored by reference in events, loaded on demand.

#### Scenario: Reference storage

- WHEN a turn emits a build-context observation
- THEN the event SHALL store a reference (`bco:<turn_id>:<seq>`) instead of the full payload
- AND the full payload SHALL be retrievable via `load_build_context_observation(ref)` returning the original payload (asserted equal)

#### Scenario: No duplicate storage

- WHEN the same observation is referenced by a timeline entry and an event
- THEN the payload SHALL be stored once (no duplication)
- AND legacy embedded data SHALL remain readable (wire field retained, only new data uses references)

### Requirement: Provider call records as projection

`TurnTraceRecord.provider_call_records` SHALL be generated by `MetricsProjection` from `ProviderUsage` events, not stored independently.

#### Scenario: Records rebuild

- GIVEN persisted `ProviderUsage` events for a turn
- WHEN `provider_call_records` is rebuilt
- THEN each record SHALL correspond to one `ProviderUsage` event (request kind, cache hit/miss, prefix mutation reasons, latency)
- AND the rebuilt records SHALL match the previously stored records on the agreed field set (clock/sequence fields exempted)
