# 元复盘：B064 尾段（Windows 全量首跑扫尾 · 并行会话切分波次）

日期：2026-11-11
范围：backlog:B064 的「未被另一在飞会话覆盖的三族 + 解阻项」，Lead + 1 名独立验收者（verifier-b064b）。
结论先行：**交付成立，但本波真正的价值来自「先验证再实施」——B064 记录在 12 小时内已两次失真**。

## 1. 通信拓扑与信噪比（Topology & Noise）

- **人工并发而非编排并发**：同仓同一工作树共有 ≥4 个活动会话（本波 Lead、B060 主线及其 3 个 subagent、「Windows 扫尾主线」）。名册不可见 ⇒ 唯一可用的协调信道是**共享工作树的 mtime + 会话日志**。本波靠读 `~/.dsh/sessions/*/session.v4.jsonl.zstd` 判定「B064 正被谁做、做到哪一步」，才避免了两队同时改同一批测试文件。
- **代价与收益**：定位冲突花了约 8 次工具调用，但换来一次真实的写域让位（a12 相位夹具：我方撤回自研写法，改用主线 `pin_carousel_phase`）。若不查，必然出现两份相位夹具并存的语义分裂。
- **噪音来源**：`cargo test` 在共享 `target-test` 上与其他会话的增量编译互相排队；一次验收者首跑 exit 101 完全是并发 lane 的半成品编译错误（`openai_sse.rs` E0599），与本次改动无关——**"并发工作区的红/绿必须带归属判定"**，否则会把自己的改动误判成回归。

## 2. 门禁穿透与误杀率（Gate Penetration）

- **穿透（险些自我欺骗）**：Windows CI 首轮失败被我一开始读成「我的改动没生效」；实际是**基线选错**——HEAD（B060 红相冻结提交）带 `unimplemented!()` 桩，整包不可编译。改用 89e2ec80 作基线后一轮见绿。教训：**验证分支的基线必须显式选「可编译的最后一个绿点」，不能默认 HEAD**。
- **真拦截**：`governance` 的 `backlog lint` 抓到了 `resolve()` 不回写 `.next-id` 的真缺陷（main 上连续多轮红），我把它当"记录卫生"忽略了 20 分钟才去读日志——**门禁红而不读，等于没有门禁**。
- **误杀**：0 条被旧门禁误杀；但发现一条**结构性恒红**：租约锁 `backlog/.locks/*.lock` 未入仓也未 gitignore ⇒ 干净克隆里任何 `in_progress` 任务都被判违规（已登记 B069，未在本波修，因为属门禁设计裁决）。
- **独立验收有效**：验收者给出「assert 110→117 / 18→19 / 16→17，`#[test]`/`#[ignore]` 计数不变」的机械口径，比我自述"没削弱断言"可信；并如实标注"r6 非 unix 分支只能由 Windows job 举证"——随后被真机收据证实。

## 3. 分工契约与隔离有效性（Contract Isolation）

- **写域声明救了两次**：① 冲突文件 `tui_dialog_wave39.rs` 在被判定为「主线写域」后立即退出；② 提交前用正则校验暂存区（`git diff --cached --name-only | grep -v <白名单>`）拦住了把别人 13 个在飞文件一起提交的事故。
- **worktree 的使用边界**：`git worktree add` 建验证分支是安全的（不动共享工作树的 HEAD），但在 worktree 内 `git push` 会触发 pre-push 的 `npm run typecheck` 而失败（无 node_modules）——**用 symlink 到主工作树 node_modules 解决，而不是 `--no-verify`**。
- **信息下发**：给验收者的 prompt 只给「改动清单 + 可复跑命令 + 不许写」，未给结论；其独立性因此成立。

## 4. 元协议迭代建议（Self-Evolving Protocol）

1. **「验证」任务的第一步必须是"取真凭据"而不是"读任务描述"**：本波 B064 的 `triage_context` 描述 ③ 为「颜色能力档位」（错，实为轮播相位）、未列「Windows 前端口单测阻断」（漏）。建议 dev-team 在 Phase 1 前加一条硬动作：**用 CI 日志/复跑取代任务描述的"剩余清单"**。
2. **验证分支基线门禁**：CI 型任务的 verify-only 分支必须显式记录 `base=<last-green-sha>`，且 base 不可为含红相冻结（`unimplemented!` / `todo!()`）的提交。建议写入 dev-team 的 "Tier-1 冒烟" 条目。
3. **并发工作区的红绿归属**：凡是共享工作区跑编译类测试，receipt 必须带「该错是否可由本单写域产生」的判定（本波靠 `git show HEAD:<file>` 与报错文件路径比对完成）。
4. **门禁数据面与代码面分离**：`resolve() 不回写 .next-id` 这类缺陷说明——**门禁脚本的"数据自洽"必须由脚本自身维护**（写入即推进高水位），不能依赖提交者记得同时提交两文件；建议把"账本 + 高水位必须同提交"做成 pre-commit 断言。
