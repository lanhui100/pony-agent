## 1. 通信拓扑与信噪比

- 拓扑：Lead + test-agent（独立验收）+ executor（实施）+ 2 路 Subagent 审查（L3-A 状态/滚动数学、L3-B 渲染/布局契约），
  符合「有状态生命周期 → Teammate；无状态局部求值 → Subagent」公理；Roster 峰值 3（含 Lead），远低于上限。
- 信噪比：teammate 回执全部按「命令原文 + 真实退出码 + 失败归属」交付，未出现空转轮询；Lead 侧没有
  重复读取同一文件的行为，重复命令仅出现在「基线 → 修复后」对照这种**有新信息**的复跑上（属必要对照，不是反重试风暴）。
- 缺陷：Lead 前期亲自做了较多侦察（约 8 次 read/grep），本应外派 Explorer；因任务边界窄（单文件）而自我豁免，
  但随后被**并发会话**的中间态反噬——该成本证明「陌生/活跃工作区的侦察更适合外派并快照化」。

## 3. 分工契约与隔离有效性

- 写域正交成立：测试文件（test-agent）/ tui.rs（executor）/ 文档与契约（Lead）/ 审查 JSON（Subagent）互不相交，
  未发生脏写；executor 与 test-agent 的**时序重叠**（A12 落盘前 F1 已实现）导致 A12 首跑即绿，
  test-agent 用「仓库外变异实验」补足了红证据——这是本轮最有效的一次自证加固。
- 隔离失效的真实风险源不在团队内，而在**工作区外**：另一会话在本轮期间持续修改同一 `tui.rs`、同一 `README.md`、
  并新增 `wave65` 单测改造进程级 `HOME`。Lead 通过「不提交 git + 只定向路径 + 回退对照实验 + 单跑隔离复验」
  把不可控面压到可解释范围（3 项红目标全部有因果排除证据）。
- 教训：多会话共享工作区时，「同一文件并发编辑」应显式升级为**写域冲突登记**（本轮合同 §0 只登记了 git 纪律，
  未登记 tui.rs 的外部写者，导致中途一次编译失败与一次 88 秒 PTY 归因开销）。

## 4. 元协议迭代建议

1. **契约条目要带"可观测方向"**：本轮 C6 只写「1 行呼吸」，未区分前驱/后驱方向，导致实现只落了一侧且验收
   只测了一侧。建议 dev-team 契约模板强制「每条渲染/间距断言必须给出双向或对称场景」。
2. **基线必须在「空桩落盘前」采集**：本轮基线在空桩之后采（PTY c9/j1 因此被误判为桩导致），多花了一轮归因。
   建议 Phase 1 基线采集点前置到任何源码写入之前。
3. **多会话共享工作区显式化**：建议 dev-team 在团队就绪门禁增加一条「工作区外部写者探测」（如观察
   `git status` 变化率 / 编译锁争用），命中即强制「零 git 写 + 回退对照实验」纪律，并要求在收据里点名外部写者。
4. **验收测试的"死代码化"检查**：`push_blank` 在空 Vec 上 no-op 这类"看起来写了其实没生效"的实现，
   应作为审查清单的固定攻击面（本轮两路审查各自命中一次同类问题）。
