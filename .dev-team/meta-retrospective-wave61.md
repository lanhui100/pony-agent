# Wave-61 元复盘（status-panel：圆环迁移 / 间距对齐 / 空值隐藏 / 入场动效）

分级 A+（单模块前端 UI）。团队：Lead + executor + test-agent + 4× Subagent（2 方案对抗、2 汇聚审查）。
红相 `b1d62f3` → 实现 `5c0eb40` → 用例缺陷重写 `cf783b0` → 收口 `427ee0b`。

## 1. 通信拓扑与信噪比

- **拓扑选择正确**：实现者（executor）与测试者（test-agent）严格分权，写域 `src/components/*.vue` vs `tests/**` 零交集；
  审查（4 次）全部下沉 Subagent，不占常驻名册（活跃名册峰值 3 人，符合容量保守引理）。
- **信噪比问题（结构性）**：本波 Lead 亲自承担了大量只读侦察（命中「≥5 文件 / ≥3 模块」的委派阈值却自留），
  代价是 Lead 上下文中堆积了 composer 1680 行、wave17 e2e 700 行等原始文本。**改进**：凡预估 ≥3 个文件或需 ≥2 轮 grep 的定位，
  一律先派 E1 Explorer 出 `path:line` 清单，Lead 只做裁决性抽验。
- **重复读取率**：契约文件被 Lead 改 6 次、被 test-agent/executor 各复读 2 次以上（R1-R8 逐条追加），
  属「原地改写」纪律执行得好的部分（未追加新章节膨胀）；但**契约版本号未显式递增**，
  导致 executor 曾按旧版 `min-w-[4.25rem]` 规划（被 Lead 及时纠正）。**改进**：契约每次改判必须带 `vN` 版本行 + 变更流水一行。
- **并发工作区风险（本波最大噪声源）**：同仓有 2 个并行会话（wave-60 stop / wave-61-team）在写
  `WorkspaceComposer.vue`、`.dev-team/state.json` 等。Lead 用「定向 `git add` + `git apply --cached` 拆 hunk」
  把本波 3 个 hunk 与 wave-60 的 2 个 hunk 分离，避免了脏写。**改进**：多会话并行时应在开工即约定
  「同一文件只允许一个会话持有」，或在 `.dev-team/state-<wave>.json` 登记文件级占用表。

## 2. 门禁穿透与误杀率

- **真拦截（有效）**：① 两路方案对抗审查（A/B）共 8 条 BLOCKING 全部为真缺陷（列宽算术、位点总数不可达、
  TransitionGroup 对 Fragment 根不下发 enter 类、HomeSidebar 断言自相矛盾、§5 漏掉哈希冻结文件），
  其中 6 条若放行会直接导致绿相失败；② 真实浏览器门禁抓住 2 个**只有物理环境才能暴露**的缺陷：
  圆环入场 `scale(0.92)` 使 bbox 被缩放（58.42 vs 63.5，jsdom 恒绿）、`grid` 自动流式下隐藏位点导致圆环落错列。
  **结论：jsdom 层"结构正确"不等于"物理正确"，UI 类任务必须保留真实浏览器门禁。**
- **误杀（1 例，已纠正）**：test-agent 的 3 条用例首轮红被初判为「实现缺陷」，实为用例缺陷
  （teleport 桩污染子节点计数、夹具未清 `contextDisplayTokens`、WAAPI 缓动口径）。Lead 逐条取证后
  以「用例自身缺陷重写豁免」授权修正，阈值零放宽，并把其中一条改成**加严**断言（恰 1 svg + 恰 1 span）。
- **门禁穿透（1 例，已记账）**：E-3 原先用 `!= null` 判定圆环可见性，0 token 会渲染 0% 空环——
  与用户"零值不显示"直接冲突，且**测试未覆盖 tokens===0**。收口时已收紧为 `>0 且有限` 并重跑门禁。
  教训：空值契约要按**每个字段的"空"**逐一列举，不能只写一句"空值不渲染"。
- **环境抖动（非断言失败）**：`write EPIPE` / `browserContext.newPage: Target page ... closed` 多次出现，
  归因为同机负载（k3s/clickhouse/prometheus/GitHub Runner）+ 浏览器进程残留。已用「清理残留进程 + retries」
  取得干净收据，并在交付说明登记 `v10-baseline-freeze` 嵌套 spawn 的既有脆弱点。

## 3. 分工契约与隔离有效性

- **契约作为唯一真值源有效**：8 条裁决（R1-R8）全部由 Lead 落盘并回灌给两个执行体，未出现"口头约定"。
  特别是 R1（缓存比率尾段移出）与 R6（tooltip 精确匹配）的**互斥冲突**被 test-agent 主动上报，
  Lead 裁决「保持两条独立 tooltip」后两边同时满足——这是"分权 + 显式契约"产生的正向收益。
- **隔离失效点**：executor 在实现中途**上下文耗尽**（未留收尾回执），剩余缺口（E-4 行折叠、R8 列位）
  由 Lead 以「栅栏装配」身份补齐（<50 行，已登记例外）。教训：A 级 UI 任务的 executor 提示里应
  显式限制"首轮只改目标文件的 2 个区块"，并预留一次收尾轮。
- **测试冻结纪律**：红相锚定后共发生 3 类测试改动——用例缺陷重写（D1-D8，逐条授权）、
  契约迁移（§5/§5.1）、冻结哈希重锚（v10）。三者全部有 Lead 授权记录与"原意图保真"说明，
  未出现"改测试让它绿"（审查员 A 复核 8 个 FROZEN_FILES sha256 仅 wave59-f2 变动且与新哈希一致）。
- **遗留未闭环（ADVISORY）**：① `browser-smoke.mjs` 迁移后第 3 个合取项在空数据环境下恒真（死条件）；
  ② R8 显式列位缺少机器断言覆盖（全位点可见时删掉 `col-start-4` 仍全绿）。两者均不阻塞，
  已登记为后续专项（需在真实浏览器 + 有数据夹具下补断言）。

## 4. 元协议迭代建议（对 dev-team skill 自身）

1. **UI 类任务的门禁清单应追加"变换感知测量"**：任何在入场动画（含 `scale`）期间测 `getBoundingClientRect`
   的断言都必须先 `await animation.finished`，或改用 `offsetWidth/offsetLeft`。本波两个失败都源于此，
   建议写入 skill 的前端门禁条款。
2. **"抽屉式"契约裁决需要版本号**：契约在同一文件内被改判 8 次时，应强制 `vN` + 单行流水，
   否则下游 Agent 会按缓存版本实施（本波已发生 1 次）。
3. **多会话共享工作区应内置 hunk 拆分脚本**：本波 Lead 手写 `git diff` 分 hunk + `git apply --cached`，
   建议把「按 hunk 归属过滤后定向暂存」固化为 skill 脚本（`dev-hunk-stage.py`），降低脏写风险。
4. **空值互斥契约应在方案阶段就举反例**：本波"空值不渲染 × 列对齐"、"tooltip 精确匹配 × 尾段合并"
   两组冲突都是**在实施中被撞出来**的；建议 Phase 1 对抗审查强制新增一问：
   "本契约的两条硬约束在极端数据下是否互斥？给出反例"。
