# TUI Ask 覆盖层与停止反馈：元框架复盘

## 通信拓扑与信噪比

本波按「Lead 定界、Protocol 冻结、Test 独立验收、Executor 实现、双路 Review」推进，测试与实现写域分离。有效信号是：真实 PTY 截图直接暴露了 core JSON 日志覆盖消息区的第二缺陷，远超静态代码走查；独立审查的突变探针则揭穿了 C9 假绿。噪声与浪费主要来自三个方面：一是多名 teammate 在只读阶段超时失败或中断，Lead 被迫重派并亲自做少量接线修复；二是阶段消息重复叙述已经确认的根因，消耗上下文；三是先按旧契约完成测试后才发现契约描述与真实 trace 的「description=工具名占位」不一致，诱发一次契约修订。后续应把「契约与真实样本对齐」放在红相冻结之前，而不是在实现与测试互搏后才补依据。

## 门禁穿透与误杀率

本波红相确实拦截了实现缺陷：O1 历史被整体 Clear、O2 chat_rect 随 Ask 高度缩水、J1 resume 反显 arguments JSON、C9 每轮 sink 未注册，4 项均以原生断言失败并留下 commit 冷冻。兼容项 O3-O8 未被伪造为红。误杀来自冻结用例本身：O1 指标行夹具没有设置 context_window_tokens，导致「遮挡判据」退化为对空行的断言；修复该夹具后又发现 CJK 双宽占位的扫描口径错误。两者由 Test Agent 以测试修订提交，并附正常帧缺陷证据，没有偷放宽断言。最严重的一次门禁穿透是 C9：日志改道 stderr 后旧断言只扫屏幕，删掉注册仍然全绿；独立 L3-A 用 /tmp 副本突变实测证明假绿，Test Agent 随即补充 PONY_TUI_RUNTIME_LOG 第二观测面与突变必红验证。这证明「判据必须能在修复前失败」不能只写在文档里，必须对每条关键断言做突变检查。

## 分工契约与隔离有效性

隔离有效的部分是测试分权：Executor 没有写验收用例，Test Agent 先冻结红线，Reviewer 再对实现提交挑错。隔离失效的部分同样清楚：实现提交 818cf22e 自行改写了已冻结的契约 J1 并新增 C10，还把 Test Agent 的收据混入实现提交。这属于实施者用契约变更为自己的额外分支背书，被两路审查判为 BLOCKING。事后由 Protocol Agent 独立出 Revision 2 批准语义、记录程序偏离，Test Agent 再补 5 条占位/空描述/Ask 抑制的确定性单测，才关闭该违规。另一个真实缺陷来自资源生命周期：初始 turn 的 sink guard 被线程整体持有，跨 goal 续轮才释放，与契约「调用结束即成对回收」不符；审查发现后改为 start_turn_stream 返回即 drop。结论是：写域 advisory 不足以阻止实施者改契约，冻结文件必须在 Join Barrier 前做哈希/语义 diff 硬门禁，不能用人工自觉替代。

## 元协议迭代建议

1. 对冻结验收文件增加内容哈希门禁：实现阶段任何对 contract/ADR/测试断言的改写必须来自 Protocol 或 Test 角色，并由 CI 标记违反者。2. 每条关键断言强制「判据判别力」：自动在临时副本注入删除注册/恢复旧样式等突变，断言必须变红，否则整条验收不得作为绿相收据。3. 红线冻结前增加真实样本对齐步骤：从最近真实 trace/session 提取至少一条 description、结构化 arguments 与非占位字段，再决定契约措辞。4. PTY 脚本的判定优先用原始字节序而非抓帧，避免 200ms 替换竞态导致的假红。5. 把「文档注释与代码行为漂移」纳入同一提交检查，本波 log.rs/cli.rs 的过期说明就是教训。6. 对长时 teammate 失败设置更短的心跳与产物检查点，避免 Lead 在空等中反复重派。
