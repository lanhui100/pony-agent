## 1. P0 — 必须改（看上去就是"坏了"，破坏美感/可用）

### P0-1 浮层一打开，品牌 P 标就退化成"灰底彩条条码"
- **截图**：`after/models-panel/main.png`（rows 5–12, cols 6–16）、`after/provider-panel/main.png`（同位置）、`after/add-provider/main.png`（同位置）
- **问题**：logo 用半块字符承载双色（上半 fg / 下半 bg）。模态压暗把 `span.style` 整体替换成 `fg(FAINT).bg(CANVAS)`（`tui.rs:2189-2196`），但半块字符的**背景像素没被覆盖**：实测这些 cell 变成 `fg=112,116,124` + `bg=渐变`。结果 P 标 20,596 px 变成平涂灰块，只剩左右边缘的橙/洋红细条——**三条场景 100% 复现，是全屏最像"渲染 bug"的地方**。
- **建议修法**（择一，按成本排序）：
  1. 模态态不画 logo（plash 是装饰，删掉最省事，也让浮层更干净）；
  2. 模态态改用"剪影模式"：把像素换成 `█`，`fg=FAINT`、`bg=CANVAS`（不要再用 `▀/▄` 承载第二色）；
  3. 若必须保留压暗后的徽标，把渐变整体乘以 0.25 后逐像素重算，而不是 patch style。
- **预期效果**：浮层打开时背景只剩干净的灰剪影或空白，焦点 100% 落在浮层上；三条场景不再出现"花屏"。

### P0-2 浮层没有清场，边框直接从字形中间切断底层正文
- **截图**：`after/models-panel/main.png`（row 15–18, col 18：`终端里的自主智|能体。` 的"智"被左边框切成半字）；`after/sessions-panel/main.png`（rows 11–14, col 28：代码块 `"name": "pony-age|` 被切）；`after/provider-panel/main.png`、`after/add-provider/main.png`（rows 14–21, col 26/28：`/provider 管理并切换模|块` 等半截字）
- **问题**：面板是"直接盖上去"的，被覆盖的背景行没有做清场，于是边框两侧留下一列半截 CJK 字形和半行代码——阅读上会误判成"内容坏了/被截断"。压暗只降低了亮度，没有解决"字形被切一半"的构图问题。
- **建议修法**：浮层绘制前，把 **chat 区整块**用 `CANVAS` 清一次（`Clear` + `fill`），再画浮层；不要保留"浮层边缘外 1~2 行残字"。若想保留上下文，则至少把与浮层矩形相交的行整行清空，而不是让边框切字。
- **预期效果**：浮层四周是完整留白，背景要么整体压暗可见（不切字），要么干净清空；三条列表/表单浮层截图不再出现残字。

### P0-3 斜杠菜单与空态列表同屏重复渲染同一条命令，且描述列差 1 列
- **截图**：`after/slash-menu/main.png`（row 19 与 row 21 各有一条 `/resume  选择并恢复历史会话`，中间只隔一条菜单上边框；rows 16–18 的空态列表被菜单压掉一半）
- **问题**：空态仍在渲染命令列表，菜单又叠在上面，同一句命令上下各一条、亮度相同，中间夹一条细线——第一眼就是"重复渲染"。另外同一份数据在空态/help 里描述列是 **16**，在菜单里是 **17**（`slash-menu/main.txt` L19 vs L21），同屏可见 1 列抖动。
- **建议修法**：`matching_commands()` 非空时**不渲染空态引导块**（或整块压暗到 FAINT 并整体上移，让菜单从列表顶部接管）；描述列抽一个常量，空态/help/菜单统一（建议 16）。
- **预期效果**：输入 `/` 时屏幕上只有一份命令表；三处列表列完全对齐。

## 2. P1 — 明显（不改也能用，但"克制"不成立）

### P1-1 "暖黑画布"名不副实：中性阶整体偏蓝，只有前景是暖的
- **截图**：所有 `after/*/main.png`（最明显：`after/empty/main.png` 大块背景 + MUTED 次级文本）
- **问题**：`CANVAS(13,14,17)` R−B=−4、`SURFACE(24,26,31)` −7、`HAIRLINE(48,51,58)` −10、`MUTED(154,157,163)` −12、`FAINT(112,116,124)` −12，**全是冷灰**；而 `INK(232,229,224)` R−B=+8、`ACCENT(198,167,126)` 是暖金。两套色温系统打架，就是"说不出的不高级"的来源。这也是骨色强调"发飘"的原因：暖字压在冷纸上。
- **建议修法**（保持明度关系不变，只转色温；对比度已核算）：
  | token | 现值 | 建议值 | 对下层的对比度 |
  |---|---|---|---|
  | CANVAS | (13,14,17) | **(18,16,14)** | — |
  | SURFACE | (24,26,31) | **(27,25,22)** | 1.08:1 vs canvas |
  | SURFACE_SEL | (38,41,48) | **(40,37,32)** | 1.15:1 vs surface |
  | HAIRLINE | (48,51,58) | **(52,47,41)** | 1.32:1 vs surface |
  | MUTED | (154,157,163) | **(162,155,146)** | 6.9:1 vs canvas |
  | FAINT | (112,116,124) | **(124,118,110)** | 4.2:1 vs canvas |
- **预期效果**：整屏统一到暖中性，骨色/金铜强调点落回同一色温，用户的"克制"诉求从"少装饰"升级为"同一口气"。

### P1-2 一种 SURFACE 材质承担了五种语义（材质语义塌陷）
- **截图**：`after/conversation/main.png`（用户块 rows 3–5 / 行内 code row 13 / composer 带 rows 29–33）；`after/models-panel/main.png`（面板底）
- **问题**：用户块、行内 code 底色、浮层底、选中行、输入带全部是 `SURFACE(24,26,31)`。于是"有底色 = 用户消息"这个你刚建立的规则立刻被行内 code 破坏——尤其行内 code 的底色是**整行高 42px**，像荧光笔涂了一整条（`conversation/main.png` row 13 的 `package.json`、`0.1.125`）。用户块的材质不再独有。
- **建议修法**：建立三段材质阶梯：`CANVAS` < **`CODE_FILL(23,22,20)`**（行内 code 专用，或干脆去掉底色只留等宽+INK_SOFT）< `SURFACE(27,25,22)`（用户块/composer）< `SURFACE_SEL(40,37,32)`（选中/浮层）。行内 code 的填充高度也应从"整行"收到"字形范围"。
- **预期效果**：一眼能分辨"这是用户说的"和"这是代码引用"，用户块重新成为唯一的块级材质。

### P1-3 用户消息的"唯一区分信号"偏弱，而 accent 语义被拉平
- **截图**：`after/conversation/main.png` rows 3–5（`▌` col 3 + SURFACE 块）
- **问题**：块与画布对比度 **1.11:1**、竖条 `ACCENT_DIM(126,108,84)` 对块 **3.45:1**。这套"面 + 条"在好屏幕上是够的，在低对比屏/投屏上会掉；而同时 `ACCENT` 被用在品牌词、助手标签、输入提示符、光标、浮层标记——**"金铜 = 身份"的语义被稀释成"到处都在用的强调色"**。
- **建议修法**：块保持 1.1:1 的低调，把竖条提到 `ACCENT(198,167,126)`（7.7:1）或中间档 `(166,144,110)`（5.7:1）；同时把 `ACCENT` 收回到"只有助手身份点"（助手标签 + 输入提示符），品牌词/浮层标记降一档。
- **预期效果**：用户块远看有块、近看有条；金铜重新变成"有含义的颜色"而不是装饰。

### P1-4 双标尺：header 发丝线与 composer 上边线粗细/边距都不同
- **截图**：`after/empty/main.png`（header 线 y62–64 = 3px，cols 3..117；composer 线 y1213–1217 = **5px**，cols 0..120）
- **问题**：同一屏两条 1px 级分隔线，一条 3px 内缩、一条 5px 通栏。这是最典型的"1px 抖动"观感来源：用户说不出哪里不对，但会觉得没对齐。
- **建议修法**：二选一并贯彻：(a) composer 也是页面元素 → 改回 `HAIRLINE` 细线且与内容列对齐（3..117）；(b) composer 是通栏 bar → header 线也通栏。推荐 (a)，因为 header/composer 都已经是"全宽 + 内容内缩"的同一套语法。
- **预期效果**：屏上只有一种分隔线粗细，上下呼应。

### P1-5 品牌词 `pony` 在同屏出现三种颜色
- **截图**：`after/empty/main.png`（header row 0 col 3 = INK 加粗；splash row 7 col 18 = ACCENT 加粗）；`after/conversation/main.png`（助手标签 row 8 col 3 = ACCENT 加粗）
- **问题**：同一个词 `pony` 一会儿白、一会儿金。品牌词是最该被固定的元素。
- **建议修法**：`pony` 字标统一 `ACCENT` 加粗；header 里的项目名 `pony-agent` 用 MUTED，二者靠字重/颜色分工。或者反过来全用 INK——但不要混。
- **预期效果**：扫视时品牌点位置固定、颜色固定。

## 4. 证据管线失真（**重要：不要按 120 宽截图去改输入区**）

- **现象**：`after/*/main.png`（120×34）里 composer 只剩下"提示符后 34 列的一小块"和"状态行 116 列"，看起来像色带断裂/不对称。`after/wide/*.png`（160×40）却是完整色带 17..143。
- **根因**：`tmux capture-pane -e` 会把**整行空白**裁掉，只留下行尾的 SGR；`tools/tui-audit/render_ansi.py` 的 `parse_ansi()` 用默认底色初始化网格（`Cell(ch=" ")` + 默认 Style），于是被裁掉的行尾格子按画布色绘制。120 宽时色带正好通栏（0..120，全行空白）→ 被裁；160 宽时色带后面还有 17 列画布、行尾有显式 `bg 13,14,17` 收尾 → 没被裁。斜杠菜单行、占位符行同理产生"色带只到文字宽度"的假象。
- **实测反证**（本次评审用 `tmux pipe-pane` 抓原始 PTY 并做最小终端模拟）：120×34 下 composer **rows 29–33 × cols 0–119 全部是 `#181a1f`**，是完整通栏色带；`›` 在 col 3、光标 col 5、`写` 在 col 7 也真实存在。
- **建议**（不在我的写域内，仅上报）：`parse_ansi()` 在换行时把"当前 SGR 背景"补满到行尾；或在 capture 侧改用不清尾空白的导出方式。**否则后续所有 120 宽证据都会误报输入区，评审结论会被带偏。**
- **对 Lead 的行动建议**：§1/§2 里凡涉及"输入区色带宽度/对称性"的都不要当缺陷；真实剩余问题只有 P1-4（线宽/边距）与 P2-2（占位符列偏移）。

## 6. 明确写明：这些是风格偏好，不算缺陷

- **徽标是否保留彩色渐变**：这是品牌决策。当前它是全屏 97% 的彩色像素（27,436 / 28,208），在"骨色 + 暖黑"体系里是唯一的高饱和物。可以**当作唯一品牌点**保留（那就要修 P0-1 的压暗，并让金铜 accent 退居身份语义）；也可以**降为双色（ACCENT_DIM→ACCENT）或骨色剪影**。两条路都成立，别当 bug 改。
- **用户块用金铜竖条 vs 中性细线**：用金铜会把"身份色"降级为表面装饰；用中性则更克制。我倾向中性，但这是口味。
- **浮层是否居中 vs 贴输入框**：当前位置（居中）与斜杠菜单（贴输入区）是两种语法，各自成立。
- **列表用 `·` 还是无 markdown bullet**：不影响可读性。
- **120 列行宽**：已在合理区间。
