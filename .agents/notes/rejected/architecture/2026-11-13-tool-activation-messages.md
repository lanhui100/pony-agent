# Agent Note: 工具增删走「激活消息」而非重排主工具表（原 6b 项）

Status: rejected — 工具面只是偶尔变化，收益不足以承担改动线上请求形状与缓存前缀的风险

## Proposal

背景：`tools` 数组属于 provider 前缀缓存的一部分。当前工具面变化（MCP 通道接入/断开/重载、插件增删）会直接改变请求里的 `tools` 数组，使整个前缀缓存失效。DSH 的做法是 `deferLoading` + developer 消息「激活」：主工具表在会话内保持不动，工具的启用/停用以追加一条 developer 消息表达，从而把「工具集变化」从**前缀变更**降级为**历史追加**（缓存前缀仍命中）。

原提案（item-6b，拟 2–3 天）：

1. 主请求的 `tools` 数组冻结为会话首轮的快照（与 `provider_contract_views()` 的当前视图解耦）；
2. 工具集变化时，追加一条 developer 消息声明「本轮新增/停用以下工具：…」，由 provider 适配层把该消息与冻结表一起下发；
3. 适配层对不支持激活语义的 provider（Anthropic 家族等）回退到现有的「重排主表」路径；
4. 以真实 provider 的缓存命中率回归作为验收口径（`cache_hit_input`），不以单元测试代替。

## Alternatives considered

- **实施本提案（继续做 6b）**：收益只在「工具面频繁变化」时有意义；用户裁决工具面**偶尔变化**（会话内基本稳定），此时前缀失效本就很少发生，而改动面覆盖请求形状、工具声明时序、三家 provider 适配与回滚路径，属于高成本换低频收益。
- **只做 6a（工具面顺序契约 + 突变原因）**：已落地 `tests/tool_surface_order_contract.rs`（TS1–TS3）+ B143；顺序漂移这条「静默成本」已堵住。突变原因部分（B144）仍待 provider 拆分后补，属观测增强、非结构性改动。
- **纯观测：先把工具面指纹写进 observation，靠 trace 统计真实失效率**：比直接改协议便宜得多，但需要动 serde 契约面（TS 快照 + 前端类型）。在「偶尔变化」的前提下，先把 B144 做完即可覆盖归因需求，不必新增指纹字段。
- **什么都不做**：不可取——顺序契约（已做）是低成本的底线；完全不做会让「调序打穿缓存」继续无保护。

## 复活条件

出现以下任一信号时重新提出本提案：

1. 真实会话里观察到工具面在**同一会话内多次**变化（例如 MCP 工具按需连接/断开的频率达到每会话多次），且 `cache_hit_input` 有明显下滑；
2. 工具数量进入「工具表本身占用可观请求体」区间，重排成本从缓存维度升级为 token 成本；
3. provider 适配层已具备统一的「工具集增量」抽象（届时改动面显著变小）。
