# Agent Note: reap 参数白名单 fail-closed，并清收两项加固待办（B107/B108）

Status: implemented

## Problem

第 5 轮独立验收给出「全部验证通过」，同时留下一条观察项（OBS-1）与两条已登记加固待办：

1. **reap 未知参数静默回落全局清锁**（B109）：`reap --id=B056`、`--ide B056`、`-id`、`--ID`、位置参数
   `B056` 都不被识别，命令以 exit 0 执行「清全部租约」。破坏性命令对未知输入 fail-open，误清并发 lane
   的锁只需一次手滑。
2. **B107（缺 `heartbeat_at` 时跳过缺锁判定）**：属 fail-open，但 CLI 产生的 `in_progress` 必带
   heartbeat；要收紧就得先定义「无 heartbeat + 无锁 + `.locks/` 存在」的语义，并承担历史/手写记录的
   误报风险。
3. **B108（`start` 取锁后 `update` 失败不回滚）**：泄漏的锁会把任务挡到 TTL 到期，但 2026-11-12 的
   租约-状态互斥判据已能在提交前把它拦成红灯，`reap --id` 可即时清锁。

## Decision

1. **reap 改参数白名单解析**：只接受 `--id <B###>`、`--minutes <N>`、`--dry-run`；其余任何 token
   （含 `--id=`、未知长选项、单横线、位置参数、非法分钟值）一律 `exit 2` 并打印用法，
   **不回落为全局清理**。全局清理只剩一种显式形态：不带 `--id` 且参数合法。
2. **B107、B108 清除（不修）**：两者都不是当前门禁的缺口——B108 已被租约-状态互斥判据覆盖（提交前红灯 +
   可即时清锁），B107 的真实暴露面是「手写记录且刻意删掉 heartbeat」这一近乎不存在的组合，收紧反而
   可能误伤历史记录。
3. **复活条件（写死以便复查，不是「以后可能用得上」）**：
   - B107：出现真实案例——`in_progress` 记录缺锁、缺 `heartbeat_at`，且 `lint`/`doctor` 双双放行并被利用；
     届时先定「无 heartbeat 是否等价于手改」的判定口径，再改 `leaseConsistency` 并补负样本。
   - B108：`start` 中断在同一工作区重复发生（≥2 次/月），或出现因幽灵锁导致的真实阻塞工时损失；
     届时在 `start` 分支做失败回滚（acquire 后 update 抛错 → release）并补 CLI 级用例。

## Alternatives considered

- **只修 `--id` 空值、不收紧其它拼写**：`--id=B056` 这类最常见的手滑形态仍会静默全局清理，
  等于只堵了一半入口 → 落选。
- **保留宽松解析、只把提示写清楚**：破坏性命令的未知输入不该靠文档免责；参数白名单是零成本的
  fail-closed，符合常载命约 2「机械可查的承诺配非零退出命令」→ 落选。
- **顺手修掉 B108（失败回滚）**：改动小但会引入新的原子性语义（回滚失败怎么办、是否写审计），
  在已有判据兜底的前提下收益低于维护面 → 本轮不做，按复活条件重开。
- **把 B107 直接收紧（忽略 heartbeat 早退）**：会让「`.locks/` 存在 + 历史 in_progress 无 heartbeat」
  的迁移记录恒红，而这类记录的真实性无法机械判定 → 落选。

## Consequences

- `scripts/backlog.mjs::reap` 参数解析改为白名单，未知输入 `exit 2`；`tests/backlog-cli.spec.ts` 的
  CLI 级用例扩为 5 类非法拼写断言（vitest 34 passed）。
- 账本清收：B107、B108 从活跃池删除（保留 `B109` 修复记录并已 `resolve` 归档）；`.next-id` 不回退，
  编号不复用。
- `backlog/README.md` 补充「未知参数拒绝」的约定；本 ADR 同时是 B107/B108 的归档理由与复活判据。
- 诚实边界：白名单只覆盖 `reap` 一个子命令；其它子命令（`record`/`start` 等）仍是宽松解析，
  但它们的未知参数不会造成批量删除（`start`/`release` 只作用于显式 ID）。
