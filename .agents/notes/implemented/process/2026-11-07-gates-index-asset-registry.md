# 门禁索引与实现同步登记（A1–A7 资产编号制）

Status: implemented

## Context

`.meta/gates/` 在 2026-11-07 前后新增了归档封印链：`archive-verify.sh`（A6）、
`archive-verify.spec.sh`（A7），并把 `ci-verify.sh`（A4）由两道扩为三段。但 `.meta/gates/README.md`
的「门禁索引」仍只登记最初的三条 PowerShell 门禁（`check-version-sync.ps1` / `git-guard.ps1` /
`verify-decisions.ps1`），完全没有 A1/A2/A4/A6/A7。

后果不是「文档难看」，而是**门禁无人看守**：

- 读者从索引出发找不到 `ci-verify.sh`，不知道本地可复现远端结论，改动只敢等 CI；
- 脚本里大量 `A4`/`A6`/`A7` 注释失去锚点，编号成了只有原作者能解读的私有暗号；
- 新增门禁时无登记义务的显式条款，漂移会持续复现（本次就是第二次）。

同类漂移已在本仓发生过一次：`ci-verify.sh` 引用 A6/A7 而索引未登记，中间隔了一个提交才被发现。

## Decision

1. **索引即资产清单，编号即契约**：`.meta/gates/README.md` 按 `A<n>` 编号登记全部门禁资产，
   编号一经分配不复用，新增只在末尾追加。
2. **按链分组而非按文件罗列**：分「决策记录链（A1–A5）」「归档封印链（A6–A7）」
   「仓库卫生与版本（PowerShell 遗留链）」，每组写清资产路径、语义、接入点（哪个钩子 / 哪一段 CI）。
3. **诚实标注未接入项**：三条 PS1 门禁明确写「未接入 A4，Linux CI 上不会执行」，
   而不是含糊地并列在同一张表里制造「已全覆盖」的错觉。
4. **登记义务写进约定**：新增/删除门禁资产必须同提交更新本索引——索引与实现漂移等于门禁无人看守。
5. **区分门禁本体与适配器**：A5（GitHub workflow）显式标注「不进宇宙表，本身不含判定逻辑」，
   防止有人把判定逻辑写进适配器再以「CI 里有」为由跳过 A4。

## Alternatives considered

- **让索引自动生成（扫描脚本注释里的 `A<n>`）**：能消除人工登记，但生成器本身需要门禁看守，
  且「语义 / 接入点 / 诚实标注」这类信息无法从脚本头注释机械抽取，会退化成路径清单。
- **只补缺失条目，不动结构**：最小改动，但仍是平铺列表，看不出资产之间的调用关系
  （A2 证明 A1、A7 证明 A6、A4 串起 verify-note.sh + A2 + A6 + A7），下一个人仍要靠读脚本才能理解拓扑。
- **把三条 PS1 门禁直接删掉以对齐索引**：删掉的是 Windows 开发机上真实在跑的检查，
  且 `check-governance.ps1` 依赖版本同步门禁；删除属于超出本决策闭包的行为变更。
- **把 PS1 门禁改写为 bash 并并入 A4**：方向正确但工作量大（`git-guard.ps1` 涉及 Windows 路径语义），
  且需要独立的负样本 spec，留作后续任务，本次只做登记与诚实标注。

## Consequences

- `.meta/gates/README.md` 现登记 A1–A7 与 3 条遗留门禁，含接入点与「未接入」诚实标注；
  脚本注释里的 `A4`/`A6`/`A7` 编号有了唯一权威解释处。
- 新增「门禁资产编号约定」「负样本 spec 的两种形态」「约定」三节，把此前只存在于脚本头注释的
  规则（自包含、`mktemp -d`、`timeout 30`、`PONYGO_IN_SPEC=1` 防递归、只读仓库、`chmod +x`）
  提升为文档契约。
- 残余风险：登记仍是人工动作，本次未加机械校验（例如「README 里提到的每个 `A<n>` 都能在
  `.meta/gates/` 找到实体」）。该反查门禁需单独设计负样本，登记为待办。
- 与本索引相关的另一处漂移已同时修正：`restore_terminal_for_signal` 的调用关系变更后，
  其 `#[allow(dead_code)]` 与两处失真注释同步清理（见
  `implemented/bug-fix/2026-11-07-tui-suspend-terminal-handover.md`）。
