# Agent Note: TUI 助手正文 GFM 管道表格块级渲染

Status: implemented

## Context

助手消息正文此前是**逐行**渲染的：`MessageRole::Assistant` 分支对每一行调用
`render_markdown_line(raw)`，只在行内处理标题/列表/围栏/`**粗体**`/`` `代码` ``。
块级结构（尤其是 GFM 管道表格）因此完全没有被识别，`| a | b |` 与 `|---|---|`
被原样打到终端上：模型输出的「参数表 / 对比表」在 TUI 里退化成一行行竖线噪音，
既读不懂也复制不出可用文本。

渲染层约束（既有设计语言，见 `tui/theme.rs` / ADR 0088）：骨色单强调、层级靠留白与
字重、分隔只用 1px 发丝线、**永不画整块边框**；且终端里画出来的任何符号都会被
「选中复制」一起带走，剪贴板里必须得到干净的纯文本。

## Decision

1. 新增块级渲染模块 `crates/pony-agent-core/src/bin/tui/table.rs`，入口
   `render_markdown_table(lines: &[&str], width: usize) -> Option<(Vec<Line<'static>>, usize)>`：
   返回「渲染好的行 + 吃掉的源代码行数」，形态不成立返回 `None` 交回逐行渲染。
2. 识别条件：首行拆出 ≥2 个单元格；次行为分隔行（每格 trim 后形如 `:?-+:?`）；
   两行列数相等。任一不满足即 `None` —— 不猜、不容错，避免把正文里的数学竖线
   （`a | b`）误判成表格。
3. 数据行自第 3 行起，遇空行 / 不含 `|` 的行 / ``` 围栏即止；列数不足补空、超出丢弃。
   单元格支持 `\|` 转义（还原为字面量 `|`），行内 `**粗体**` 与 `` `代码` ``
   复用 `markdown::parse_inline_formatting`（该函数可见性放宽为 `pub(super)`，逻辑零改动）。
4. 视觉：表头 span 追加 `BOLD` + `INK`；数据行沿用 `INK_SOFT` 与行内强调/代码配色；
   表头下方一条 `─` 发丝线（`theme::HAIRLINE`），长度 = 表格实际占用宽度；
   列间固定 2 空格，**不画 `|` 与任何竖线**，最后一列不补尾随空格，复制即干净文本。
5. 对齐：`:---` 左、`---:` 右、`:---:` 居中、默认左。最后一列不补尾随空格，
   因此右对齐/居中只表现为前导留白（视觉成立，文本干净）。
6. 宽度：自然列宽用 `str_width`（宽字符 2 列）；`sum(cols) + 2*(n-1)` 超宽时反复
   收窄最宽列，单列下限 4；仍放不下（终端太窄 / 列太多）返回 `None` 走原样渲染。
   单元格超列宽按列宽折行，复用既有 `wrap_line`（含行首禁则）。
7. 接线：`MessageRole::Assistant` 的 `for` 逐行循环改为索引 `while`（`src: Vec<&str>`），
   在 `in_code` 判定之后、普通行渲染之前尝试表格块；命中则整块输出
   （每行仍 `push_prefixed(..., rail_blank(), rail_blank(), line, body_w)`），
   块前后各 `push_blank` 一次呼吸。未命中时围栏/空行/普通行分支与改前逐字节一致。
8. 回归测试 `table::table_tests`（4 条）：2×2 表在 width=60 下行数 = 1 表头 + 1 发丝线
   + n 数据行且同行可见两列文本；缺分隔行 ⇒ `None`；width=20 时每行 `str_width ≤ 20`；
   行内 `` `code` `` 渲染后不残留反引号。
9. 接线回归 `tui/tests/table_wiring_tests.rs`（2 条，走公开入口 `message_lines_for`）：
   `table.rs` 自身全绿而调用点被摘掉/切片起点算错时同样无人报警，故端到端断言
   （a）助手正文的表格渲染后全文无 `|`、含发丝线、同行可见两列且表格前后段落都在；
   （b）``` 围栏内的表格原样保留且不生成发丝线——围栏优先级高于表格识别。

## Alternatives considered

- **引入 `pulldown-cmark` / `tui-markdown` 等依赖**：为一张表格拉进完整 CommonMark
  解析器，编译时间与依赖面（以及供应链审核成本）都远超收益；而且这类库产出的是
  HTML/AST 或**自带的**样式体系，与本仓 `theme.rs` 单一真值源、无边框发丝线的设计
  语言冲突，最后仍要写一层「AST → 本项目 Line/Span」的适配代码，反而多一坨不能删的
  中间层。现有 `render_markdown_line` 已经是手写行内解析，块级只差「表格」这一种形态，
  200 行局部实现足够且可控。
- **带 `│` 竖线边框（含 `┌─┬─┐` 完整框线）**：终端里画出来的竖线会被选中复制带走，
  粘进 issue/PR/聊天后全是 `│` 噪音；框线还会带来「卡片」观感，违反本仓
  「分隔只用发丝线、永不画整块边框」的既定规范。列间 2 空格 + 表头一条发丝线
  已经足以表达列边界，且复制出来是干净文本。
- **超宽只截断（`ellipsize_width`）不折行**：截断会静默丢信息，表格单元格里往往是
  枚举值/参数说明，`…` 之后的半句恰恰是决策依据；而且窄终端（80 列下两列中文表）
  会几乎截掉全部内容。折行保留全部文本，行高增加是可接受的代价；真的塞不下
  （收窄到单列 4 仍在宽度外）才整体退回原样渲染，把「可读性」与「不丢信息」的取舍
  交给用户可感知的兜底路径，而不是悄悄删字。
- **保留 `|` 但做等宽对齐**：管道符仍会被复制走，且中英混排在终端里本来就难对齐，
  不如干脆去掉符号、只用留白表达列结构（与 TUI 其它「去符号噪音」的改动一致）。
