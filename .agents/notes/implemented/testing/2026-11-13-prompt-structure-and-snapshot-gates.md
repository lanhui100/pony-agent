# Agent Note: 稳定层提示词的结构门禁与团队策略段全文快照

Status: implemented

## Problem

稳定层提示词的既有门禁全部是「片段」维度的：

- `tests/system_prompt_contract.rs`（SP1–SP10）只断言某些短语存在、某些旧措辞缺席；
- `tests/prompt_tool_consistency.rs`（PT1–PT6）只校验工具名与冻结契约文档的对应关系，其中 PT5 冻结的是 BASE 全文；
- `wave61_team_activation` 对团队策略段同样只做片段断言（锚串、`Run`、`cas_conflict`、不含 `FS_STALE_VERSION`）。

因此三类真实漂移**都不会变红**：①把某段整体换到别的位置（顺序错乱但片段都在）；②新增一段与既有段落语义冲突的说明；③团队策略段被整段改写、但锚串与工具名仍保留（这是最容易发生的：该段没有任何全文冻结）。

同时，SP9 的「`<= 3900` 字节」护栏在 BASE 全文已被 PT5 逐字节冻结后已成冗余：任何超出都会先在逐字比对处失败，护栏只剩「非空」这一点剩余价值。

## Decision

1. **新增结构门禁** `crates/pony-agent-core/tests/system_prompt_structure.rs`（ST1–ST3）：
   - ST1：BASE 顶层条目按固定顺序各出现一次（顺序用「按序定位 + 全局出现次数 == 1」判定，不依赖脆弱切片），顶层项目符号数冻结为 9；
   - ST2：团队策略段顶层条目同样按序冻结，项目符号数冻结为 9；
   - ST3：团队策略段全文与 `tests/fixtures/team_policy_prompt.txt` 逐字节比对 —— 补上该段此前**完全缺失**的全文冻结。
2. **保留逐字冻结、不把字节断言降级为软告警**：`base_system_prompt().len() == 3790` 与契约 §6 的登记值由 PT5 双向比对，这是「文案只能在契约内改」的强约束；软化它等于放弃承诺。SP9 的 `<=3900` 护栏不动（新增会先在逐字比对处失败，护栏仅作纵深防御），但不再作为主要防线宣传。
3. **契约升 v2.3.0**：§7 增加 ST1–ST3 三行，明确「片段断言查不出结构漂移」这一动因；渲染文本与字节数不变。
4. **快照的维护方式**：改团队策略段文案 → 同提交更新 `tests/fixtures/team_policy_prompt.txt`，并在提交信息里给出理由；快照文件带 POSIX 结尾换行，比对时两侧 `trim_end`。

## Alternatives considered

- **把字节断言降为软告警（只留 `<=` 上限）**：原本第 7 项建议这么做，但契约回填后 BASE 已有逐字冻结（PT5 ⇄ §2），软化只会削弱约束且不增加任何覆盖；否决。
- **再补一份 BASE 全文快照文件**：与 PT5 的契约文档比对完全重复（同一份真源两份拷贝，反而增加漂移面）；否决，BASE 的全文冻结继续由契约文档承担。
- **用行号区间断言结构（`lines[3]` 是某段）**：对空行/换行风格极度敏感，一改格式就红且报错难读；改为「锚点顺序 + 出现次数」。
- **把 ST 断言塞进 `system_prompt_contract.rs`**：该文件是独立测试方交付物、实施者只读不可改；新建文件避免触碰冻结测试。
- **团队策略段不加全文冻结**，只加顺序断言：仍挡不住「同位置整段改写」——而这正是该段最容易发生的漂移形态（它没有别的全文真源）。

## Consequences

- 三类结构漂移现在各有对应断言：段落换位/新增段（ST1/ST2）、团队段整段改写（ST3）。
- 变异验证（临时改动后还原，sha256 校验）：把 BASE 中两条项目符号交换顺序 → ST1 立刻失败并指出具体锚点；恢复后重新全绿。
- 成本：每次**有意**改结构都必须同提交更新锚点常量或快照文件，属于预期摩擦（契约面本来如此）。
- 残余：ST 断言只覆盖顶层条目，子条目（`  * …`）的顺序仍无门禁；团队策略段之外的动态层（semistable/volatile）结构由 `context.rs` 的拓扑单测覆盖，不在本条范围。
