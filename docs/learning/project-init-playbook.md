# 项目 Init 指导：四层记忆系统基础设施

> **状态**: v0.1 渐进构建中 —— 随「优秀软件工程项目的七个维度」课程逐课完善
> **来源**: deepseek-harness 工程体系研读 + pony-agent 四问审计实践
> **用途**: 新项目启动期的建设指导 & 既有项目的健康审查记分卡

---

## 使用方式

- **新项目启动**：按 §2 的 Day-1 清单逐项建立最小机制，宁可粗糙、不可缺席。
- **既有项目审查**：按 §3 记分卡打分（证据优先），每个缺口必须落成一个最小改进动作。
- **本文档自身**：遵守它宣讲的原则——每个章节最终都要回答"这条如何被验证"，不能只停留于散文。

## 1. 第一性原理（已定稿）

### P1 记忆瓶颈原理
代码只承载"是什么"；团队真正丢失的是"为什么这样"和"为什么不那样"。任何只存在于人脑或聊天记录里的决策都会随人员流动蒸发。

### P2 可验证性原理
约定的生命力 = 它的可验证性。靠自觉遵守的约定在规模和人员变化下必然衰减（实证：规则写着禁止一次性 target 目录，根目录仍躺着四个违例目录）。凡机械可查的承诺，配一条非零退出的命令。

### P3 载体分工原理
一次性判断（note）、当前事实（doc）、重复程序（skill）、恒定约束（gate）必须分开存放。四层混装，文档必腐烂。

## 2. 启动清单（Day-1 部分，第 1 课可写范围）

来自 dsh 的时序证据：地基和第一块砖同一天浇筑——架构不变量、质量门禁、测试策略三类根基不晚于第一个功能。

| 层 | Day-1 最小可行机制 | 升级路径 | 对应课程 |
|---|---|---|---|
| 决策 | 建 `docs/decisions/`，ADR 格式含"候选方案+取舍" | 生命周期状态机 + 强制覆盖规则 | 第 2 课 |
| 程序 | 高频操作写成脚本并入库 | 项目自著 skills（含校准样例） | 第 3 课 |
| 强制 | pre-commit 一条卫生门禁（哪怕只拦产物和大文件） | 本地快 / CI 全的分层门禁 | 第 4 课 |
| 退场 | `.gitignore` 覆盖所有产物目录；临时文件只准进 `tmp/` | 归档冻结制 + rejected 保留判据 | 第 6 课 |

**启动期三禁**：
1. 禁止"先跑起来以后再补规范"——补规范的时机永远不会到来；
2. 禁止把决策只写进聊天记录——聊完落 ADR 才算结束；
3. 禁止无证据的约定——写进文档的每条"必须"要么配命令，要么标注"暂靠自觉 + 违例即机械化"。

## 3. 审查记分卡（四问法）

对任何项目依次回答，**先找磁盘证据再打分，不看 README 自述**：

1. **决策记在哪？** 有没有专门载体？覆盖面靠规则还是靠自觉？被击败的选项有没有留痕？
2. **承诺怎么强制？** 文档里的"必须/禁止"有几条变成了非零退出命令？强制是单点（本地 hook）还是分层（本地+CI）？
3. **重复劳动怎么复用？** 高频+高判断力流程是口传、一次性交接文件，还是入库的可复用资产？
4. **过时的怎么退场？** 归档机制存在吗？工作区里有没有过期产物堆积（杂物堆是缺失的活证据）？

评分纪律：
- 每问 0–10 分，锚点见各课内容（随课程补充）；
- 每个缺口 → 一个**最小改进动作**（审计不产出行动清单就是吐槽）;
- 缺口之间找杠杆：**强制层是其他三层的放大器**，资源不足时优先投它。

## 5. 决策生命周期工程（第 2 课）

### 5.1 生命周期状态机：状态必须可机械验证

```
proposed/ ──→ implemented/ ──→ archived/
    │
    └────→ rejected/
```

- 状态编码在**路径**中（`{lifecycle}/{class}/yyyy-mm-dd-topic.md`），文件头 `Status:` 行与所在文件夹交叉验证——三重锁定（结构+内容+门禁）；
- **转换即改写**：proposed → implemented 时，`## Proposal` 必须重写为现在时 `## Decision`，验收标准/风险折叠进 `## Consequences`——移动文件夹的那次提交必须完成这次改写，门禁强制；
- **两条铁律的分离**：
  - implemented 记录的**事实**（路径、名称、默认值）必须随代码同 PR 更新——它是活的当前态描述；
  - **决定本身不可改**——推翻 = 新增记录 + 双向链接，历史不可篡改。

> 自查问题：你的决策记录里，一条记录的"死活"由什么决定？如果答案是"读者自己判断"或"索引标题里的一句话"，状态就还没有被工程化。

### 5.2 Alternatives Considered 强制制

> "A decision recorded without what it beat invites re-litigation." —— dsh notes/README.md

- 每条决策记录强制包含"候选方案与落选原因"节，格式门禁检查其存在性；
- 备选方案是决策的**有效期标签**：结论会过时，但比较记录告诉你何时该重新审视（当某个落选方案的前提条件改变时）;
- **诚实条款**：备选方案只能记录、不能编造。历史记录无据可查时，用固定标记承认空白，不许事后补造理由。

注意区分：单选项的利弊权衡（好处/代价）≠ 候选方案比较。前者回答"这个方案好不好"，后者回答"为什么不是那一个"。

### 5.3 Rejected 是护栏资产

- 保留判据不是年龄、不是字数，而是**再犯可能性**："落选方案仍是一个诱人的、有意义的错误"时才保留；
- 一条合格的拒绝记录 = 诱惑是什么 + 为什么输 + 复活条件（"等 X 出现后可重新评估"）;
- 拒绝记录的状态行是唯一允许带内容的枚举值（`rejected — <一行理由>`），因为拒绝理由正是读者来看的东西。

### 5.4 Supersession 审计（语料的 GC）

每次新增记录触发一次范围化审查：搜索覆盖同一决策的既有记录，分类完全/部分取代并**在同一变更中处理**——债务不过夜。没有它，决策语料会在几个月内腐烂成噪音。

### 5.5 最小可行改造清单（从 6 分到 9 分）

1. 每篇 ADR 加 `Status:` 行；建 `docs/decisions/rejected/` 子目录；
2. ADR 模板加必填节"候选方案与落选原因"；无据可查的历史记录标注留白而非补造；
3. 项目约定加一条：非平凡变更同一提交内带 ADR 或明确豁免说明；
4. 修复取代断链：被取代的 ADR 文件头部加 `Status: superseded by 000X` + 链接；
5. （机械化阶段）一个校验脚本：Status 行 ↔ 所在目录一致性 + superseded 链接有效性。
