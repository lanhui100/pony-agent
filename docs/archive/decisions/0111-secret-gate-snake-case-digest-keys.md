# 0111 密钥门 64-hex 规则：snake_case 摘要键与结构化摘要槽的误报收口

Status: implemented

> 修订对象：`.dev-team/contract-matrix-wave18.md` §4.2/§4.3/§4.8 的冻结规则（`BENIGN_RE` 与豁免面）。
> 本次**不改** 64 位长度窗口、不改 `(?<![0-9a-fA-F])`/`(?![0-9a-fA-F])` 边界、不改 G1–G16 必须命中的反例面、
> 不改 `.env.example` 与 `check-secrets.spec.ts` 的文件名豁免链路。契约侧以 §AMEND-6 追记。

## 背景

`scripts/check-secrets.mjs` 的裸 64-hex 规则（wave-18 C4）在真实取证产物上系统性误报，
导致 trace 审核的历史轮（`docs/audit/rounds/r1-dim6`、`r2-dim1`）**无法入库**：
`npm run secrets:check:all` 一旦面对这些文件即变红，而它们是「摘要收据」不是「凭证」。

实测（272 个未跟踪的取证文件、修复前实现）：

| 误报形态 | 计数 | 代表行（已脱敏） |
|---|---|---|
| snake_case `*_hash` 键 | 9 | `"corpus_hash": "<64hex>"` / `"expected_hash"` / `"new_hash"` |
| 中文摘要标签 | 2 | `冻结值 <64hex>` / `现值   <64hex>` |
| 非凭证键的 JSON 值槽 | 54 | `"scripts_assertions_dim6.sh": "<64hex>"` / `"before"` / `"after"` / `"detail"` |
| **合计** | **65** | 全部为误报，零真阳性 |

根因两条，各自独立：

1. **词边界失明**：`BENIGN_RE` 用 `\bhash\b`，而 `_` 属 `\b` 的 word 字符 ⇒ `corpus_hash` /
   `expected_hash` / `new_hash` 里 `hash` 两侧都没有词边界，良性关键词豁免（豁免 1）整条失效。
   这与 §4.3 自己写下的理由（「`_` 是 `\b` 的 word 字符，`\b` 会漏」）互相矛盾：那条论证只被用在了
   hex 边界上，没有被用到良性词边界上。
2. **豁免面缺口**：豁免 1–4 只认「行内出现摘要词」「sha256sum 前缀槽」「Markdown 单元格槽」
   「反引号包裹」四种形态。JSON 收据的**结构性事实**是「键 → 值」，其中值槽里放的是摘要——
   但旧实现完全不看键名，只按整行文本猜。`"before"/"after"/"detail"/"t01-list-summarize.md"`
   这类键没有摘要词，于是 54 条摘要值全部判违规。

第 2 条是**门禁设计问题**而非措辞问题：把「这个 hex 是什么」交给行文本猜测，任何新的收据 schema
都会再误报一轮；而真正需要拦的「凭证键 → 值」恰恰是**结构化可判定**的。

## 决策

### 1. 良性词边界改为「非字母数字」而非 `\b`

```
BENIGN_RE:  ...|\bhash\b|...   →   ...|(?<![a-z0-9])hash(?![a-z0-9])|...
```

`(?<![a-z0-9])` / `(?![a-z0-9])` 让 `_`、`-`、`.`、空格、行首尾都成为可接受的边界，同时
`hashtag` / `hashed` 仍不构成豁免（S11/S12 用例锁死）。同批把两个已确认的摘要标签补进词表：
`frozen_expected`、`冻结值`、`现值`——它们与 `sha256`/`指纹` 同类，是「值即摘要」的显式声明。

### 2. 新增豁免 5「结构化摘要槽」

在 `hexLineFacts` 里按行预计算 `digestSlots`（`JSON/对象成员 "键": "` 的值起始下标 → 键名），
判定时 `matchIndex` 命中槽位即豁免。**凭证键永不入表**：

```
CRED_KEY_STEM_RE = /token|secret|pass(?:word|wd|phrase)|pwd|key|cred|auth|bearer|cookie|session|signature/i
```

采用**正向「键名不含凭证词干」**，而不是反向「键名不匹配 `CRED_WORD_RE`」。后者会漏掉
`apikey` / `secretkey` / `passphrase` 这类连写形态——正是 §4.5 B3 登记的既有窄口。正向黑名单顺手把它关掉：
`"apikey": "<64hex>"` 现在判违规（T3），而修复前是放行的。

### 3. 判定顺序不变，豁免 5 置于最后

`R1′ 位置敏感 → 豁免 1 → 豁免 2/3 位置锚定 → 豁免 4 反引号 → 豁免 5 结构化槽`。
`R1′` 仍先行：`"client_token": "<64hex>"` 中凭证词在 hex 之前、且其前无良性词 ⇒ 直接判违规，
根本走不到豁免 5（T1 用例锁死）。

### 4. 零误报由红相基线 + 端到端用例双向锁死

`tests/check-secrets.spec.ts` 新增 `ADR 0111` 描述块（S1–S13 / T1–T6），其中：

- S1–S10：修复前 10/10 命中，修复后必须 0 命中（红相基线已用 HEAD 版实现实测确认）；
- T1–T6：凭证键值槽必须命中，含 `apikey`/`secretkey`/`passphrase` 连写形态；
- S11–S12：`hashtag`/`hashed` 不得被豁免；
- S13：`docs/audit/rounds/**` 端到端 0 违规（修复前 65 条）。

### 5. 性能不得回退

`digestSlots` 在 `hexLineFacts` 内按行预计算一次（与既有 `prefixSlot`/`cellSlot` 同层），
`isSafe` 内仍是 `Map.has` O(1)。实测（同机对比 HEAD 版）：

| 输入 | 修复前 | 修复后 | 判据 |
|---|---|---|---|
| 单行 1MB / 15000 hex | 35 ms | 39 ms | — |
| 单行 5MB / 77000 hex | 148 ms | 132 ms | ≤2000 ms |
| 单行 10MB / 154000 hex | 258 ms | 273 ms | ≤5000 ms |
| 149KB 单行 JSON / 2000 键 | 3 ms | 3 ms | — |

## 已知边界（诚实登记，非隐藏豁免）

豁免 5 是「按结构判摘要」的必然代价：它无法区分「这个键名下的 64-hex 是摘要还是凭证」，
只拦得住**键名本身**含凭证词干的情形。实测确认的漏报面（`wave18 §4.5 B6`）：

| 输入形态 | 判定 | 为什么接受 |
|---|---|---|
| `{"value": "<H>"}` / `{"data": "<H>"}` / `{"content": "<H>"}` | 0 命中（漏报） | 泛化键名。收紧需改成「键名必须显式含摘要语义词」（`*hash`/`*sha256`/`*digest`），但那会让 54 条 `"<文件名>": "<H>"` 形态重新误报 —— 需连收据 schema 一起改 |
| `{"payload": "<H>"}` / `{"env": "<H>"}` | 0 命中（漏报） | 同上 |
| `{"Authorization": "<H>"}` / `{"cookie": "<H>"}` | **1 命中**（正确拦截） | 键名含 `auth`/`cookie` 词干，走不到豁免 5 |

取舍理由：本次的目标是「让摘要收据不再误报」，而**零误报是绑定约束**（门禁跑在 `npm run verify` 上）。
在「误报阻塞全量自检」与「泛化键名下 64-hex 凭证漏报」之间，只能选前者；后者与既有 B1/B2/B3
同属一类已知窄口，登记而非隐藏。收紧路径（键名正向白名单 + 收据 schema 改造）属独立议题。

## 候选方案（Alternatives considered）

- **A. 只在 `docs/audit/**` 做路径级豁免**（比照 `isExemptGeneratedReceipt`）——落选。
  取证目录之外同样存在 `*_hash` 形态（`.dev-team/**` 的收据今天靠反引号/单元格豁免**侥幸**没炸，
  换个 writer 不加反引号就会炸）。按路径豁免是把「结构性误报」变成「路径白名单」，误报只是被赶走。
- **B. 只修词边界（不做豁免 5）**——落选。实测残余 55 条误报，`r1-dim6`/`r2-dim1` 仍无法入库，
  等于本次改动不解决问题。
- **C. 豁免 5 用反向判据「键名不匹配 `CRED_WORD_RE`」**——落选。`apikey`/`secretkey`/`passphrase`
  在 `CRED_WORD_RE` 下不匹配（缺分隔符），会被当成良性键 ⇒ 把真凭证放行，比现状更危险。
- **D. 把 JSON 收据里的摘要统一改写为 `sha256:<hex>` 前缀**——落选。取证产物是**证据**，
  为迁就门禁改写证据等于伪造收据；且改写后 `assertion_hashes` 的键值对语义会失真。
- **E. 用 32-hex/64-hex 双窗口 + 熵阈值替代白名单**——落选。`Cargo.lock` 的 `checksum` 面
  662+470 条即同尺寸 hex，熵判据无法区分凭证与校验和；且会推翻 §9.1 R1 的「32-hex 不覆盖」裁定。
- **F. 直接改 `.dev-team/contract-matrix-wave18.md` §4.2 冻结实现**——落选。契约正文是当时事实的
  收据，冻结实现逐字交付给了 Executor；改写它等于篡改历史。改为新增 §AMEND-6 追记修订，
  与 §AMEND-5 同惯例。

## 不可逆面与恢复条件

- **不可逆**：词表收紧（`hashtag` 不再豁免）与豁免 5 的凭证键黑名单会改变**已入库文件**的判定结果；
  若某历史收据曾依赖 `hashtag` 词形豁免，修复后会变红。当前树实测 0 违规（`--all` Exit 0），故未发生。
- **恢复条件**：若豁免 5 造成真阳性漏报（凭证键被误判为摘要键），回退方式为删除 `digestSlots`
  三处（常量、facts、判定分支）并把 `BENIGN_RE` 还原为 `\bhash\b`；S1–S10 用例随之转红即为
  「已回退」的机器信号。**词边界修复（第 1 条）不建议单独回退**：它是纯缺陷修复，回退等于恢复误报。
