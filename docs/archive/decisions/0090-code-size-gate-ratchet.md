# ADR 0090：代码规模门禁采用「基线棘轮」，只判新增超限

Status: implemented

## 背景

仓库此前没有任何可机器检查的规模上限。`crates/pony-agent-core/src/bin/tui.rs` 长到 15336 行、
`tui_event_loop` 2320 行 / 嵌套 16 层而无人拦截，就是「没有护栏」的直接后果（ADR 0089）。

同时，全仓一次扫描已有 **70 条**存量超限（`agent/tools.rs` 14816 行、`control_plane/mod.rs` 10615 行、
`turn_stream.rs` 里两个 1500+ 行函数等）。若直接把「超限即失败」接进 `npm run verify`，
仓库当天就永久红，逼迫贡献者去改这些文件以外的无关大文件，或干脆关掉门禁 —— 两种结果都比没有门禁更糟。

## 候选方案 / Alternatives considered

- **A. 全仓硬门禁（超限即失败）**：落选。70 条存量债会让 `npm run verify` 立刻红；「让门禁变绿」
  的唯一出路变成大规模重写无关文件，违背最小闭包原则。
- **B. 只扫描 `src/bin/tui*` 一个目录**：落选。能立刻绿，但护栏只护住本次重构的文件，
  其它模块继续无约束增长，且日后想扩范围仍要面对同样 70 条存量。
- **C. 只提供报告型命令（永不失败）**：落选。不会失败的检查等于没有检查（宪章「机械可查的承诺
  必须配非零退出」）。
- **D. 基线棘轮（采用）**：全仓扫描 + 基线文件记录「当前允许的最大值」，
  违规值 ≤ 基线值判放过，> 基线值或基线里没有该条目判失败。存量不阻塞合并，新增债当场拦截。
- **E. 用文件顶部豁免围栏逐文件登记**：作为补充而非主方案（采纳为围栏语义）。
  围栏适合「这个文件天生就该大」的正当例外，但要 70 个文件各写一行，且没有「只许变小」的约束。

## 决策

1. `scripts/check-file-size.mjs`（纯 Node ESM、无第三方依赖）扫描 `crates/**/*.rs` 与
   `src-tauri/src/**/*.rs`，判定三条阈值：单文件 ≤3000 行、单函数 ≤200 行、单函数花括号嵌套 ≤8 层。
2. 基线文件 `scripts/file-size-baseline.json` 由 `node scripts/check-file-size.mjs --update-baseline <path>`
   生成，**只能通过人工 review diff 后提交**；`npm run size:check` 固定以它为准。
3. 基线键 = `kind | path | name | occurrence`：
   - 不含行号，避免行号漂移造成假失败；
   - 含同名函数出现序号，避免 `projection.rs` 里两个 `apply`（388 / 223 行）互相覆盖；
   - 值比较用「违规值 ≤ 基线值」，故文件变短、函数变短都不会失败，只是产生可删的瘦身项。
4. `exempt-*` 类违规（豁免围栏过期 / 缺理由 / 日期非法）**永不进基线**，一律判失败：
   `// ponylint:file-size-exempt [until YYYY-MM-DD] <理由>` 是限时围栏，不是永久免死金牌。
5. 退出码：0 通过；1 存在新增/恶化超限；2 脚本自身错误（扫描根不存在、参数非法、基线不可解析）。
6. 接入：`npm run verify` 增加 `npm run size:check`；`npm run size:check:update` 仅在
   「确实要接受新债」时手动执行，且必须在同一次提交里说明理由。

## 影响

- 新增超限立即红，存量债记在基线里可见、可逐步删除（每次删除都会在 `--json` 输出里体现为 shrunken 项）。
- 判定是词法级的近似（注释/字符串/raw string 抹空后花括号配平），不追求语义精确；
  宁可偶尔漏报，也不制造需要人工核对的假失败。
- 基线不是豁免名单：文件继续变长会被判失败，想「靠更新基线放行」必须留下 review 可见的 diff。
- 该门禁不覆盖 TS/Vue 侧与文件内关注点数量，属已知边界，不做过度承诺。
